# 产品定位

## 产品主张

Wing-Dog 不是替用户做主的“感情裁判”，而是同时处理情绪、信息和行动的恋爱决策助手。默认主路径帮助男性从没有具体对象开始，自然增加认识女性的机会，建立互动、判断互惠、提出邀约、验证线下适配并在合适时确认关系；缺乏互惠或不适配时，体面退出并回到自己的生活和其他可能。已有关系场景帮助用户从叙述、聊天材料和现实事件中区分事实与读心，再把建议转成可执行的下一步。

## 核心用户与价值表达

| 用户 | 典型困境 | 价值表达 |
| --- | --- | --- |
| 尚无具体对象、希望交女朋友的男性 | 不知道如何自然认识女生，容易把脱单变成期限任务 | 从真实生活和可持续渠道增加机会，每次只推进一小步，不设配额或保证 |
| 暧昧与约会中的用户 | 看不懂信号，不知道怎样推进 | 把互动整理成互惠证据，给出邀约、观察窗口和停止条件 |
| 提供聊天记录的用户 | 截图、文本、转述和线下事件混杂 | 区分来源、原文、事实、推测和未知，再生成可发送回复 |
| 冲突中的伴侣 | 想连发、质问、冷战或分手 | 先降低冲动成本，再表达感受、边界和具体请求 |
| 多人选择中的用户 | 心动、稳定和现实可行性冲突 | 分开维护人物，比较互惠、可靠、现实和长期选择权 |
| 分手或背叛后的用户 | 想复合、报复、自责或无法停止关注 | 区分止痛冲动与可修复证据，设计恢复、验证或退出路径 |
| LGBTQ+ 与多元关系用户 | 普通建议预设异性角色或单一婚姻脚本 | 以知情同意、互惠、现实条件和真实目标判断 |

## 差异化能力

1. 从无对象到确认关系：把增加机会、互动、互惠、邀约、线下适配、确认和退出串成路径。
2. 情绪与决策一体化：确认用户当下能否执行，而不只给分析。
3. 多人档案：一个 owner 对应多个人物，每个人物绑定独立群和 MySQL 档案。
4. 行为证据优先：人格标签只生成问题，不直接生成结论。
5. 聊天材料识别：区分截图、导出文本、转述、通话、线下和混合素材。
6. 即时话术与演练：先给首选成品，再提供反馈分支。
7. 主动约会支持：帮助表达喜欢、准备见面并依据反馈调整。
8. 跨学科按需路由：只加载当前必要资料，不全量塞入上下文。
9. 明确停止条件：把“再看看”变成可观察、可退出的行动计划。
10. 可追溯关系回忆：搜索只返回 MySQL 权威事件，派生增强只帮助找到它们。

## 非目标

- 不诊断心理疾病，不替代心理治疗、医疗、律师、警方或紧急服务。
- 不预测特定对象一定会爱上用户，不承诺脱单时间或行动配额。
- 不帮助绕过同意、拒绝、隐私或法律边界。
- 不用 MBTI、性别、性取向或星座决定关系命运。
- 不向微信、抖音或任何女性自动代发消息。
- 不在本批实现联网搜索、向量检索或本地 embedding。

## 产品成功信号

- 回答准确区分事实、推测和未知，素材来源不串线。
- 给出明确建议、理由、下一步和停止条件。
- 普通推进不反复劝退，持续低互惠时不继续加码。
- 同一人物旧事实可被有界检索召回，不要求全量历史进入上下文。
- 不同人物、渠道和 draft 不串线，明确 correction 优先。
- 高风险场景切换到安全优先流程。

## 路线图

- 持续完善 MySQL 关系档案、导入/导出、纠正/忘记、归档、迁移和恢复验证。
- 建立匿名合成回答评测，覆盖约会、冲突、选择、分手和危机。
- 为引用资料补充更新时间、来源类型和复核状态。
- 扩展地区化法律/求助信息和多语言内容。

## PRD：MySQL 增强检索与有界关系上下文

### 文档状态

| 项目 | 内容 |
| --- | --- |
| 状态 | 实现、生产迁移、历史补强和运行态发布完成 |
| 版本 | schema v5 / plugin 1.5.0 |
| 日期 | 2026-08-12 |
| 范围 | 私有 Hermes runtime；Codex Skill 分发面不新增持久化依赖 |

### 背景与问题

第一版把大量历史直接拼入上下文，事实覆盖较高，但输入长、会话成本高。向量检索方案需要本机 embedding 与 Milvus，带来显存占用、模型加载等待和额外服务状态。目标是在不新增服务或 Python 依赖的前提下，将在线检索全部收敛到已有 MySQL 8，使上下文显著变短，并尽量保持第一版全量历史的事实与行动质量。

关系原始事件必须继续是唯一事实依据。主模型在正常写入时同步生成摘要、概念、别名、实体和时间线索，只作为可删除、可重建的 MySQL 检索路标；它们不能升级为事实或直接进入最终回答上下文。

### 目标

1. 在线搜索不调用 Ollama、Milvus、本地 embedding 或后台常驻模型。
2. 默认只向主模型返回 Top-8 权威事件，单条最多 1200 字符、总正文最多 6000 字符。
3. 中文同义改写检索接近全量历史 oracle：Recall@5 >= 90%，MRR@5 >= 0.80。
4. 80 条 frozen 回答对照中关键事实覆盖率 >= 95%，首选行动/停止方向一致率 >= 90%。
5. 10000 条合成事件下 MySQL 检索 P95 <= 250ms，单次 <= 500ms。
6. 人物、渠道、draft、correction 和数据库失败关闭合同不回退。

### 当前主模型上下文合同

最终请求由 Hermes 基础 `system`、临时平台/插件 `system` 尾部、首轮 `SKILL.md` user 脚手架、会话历史和关系 `channel_prompt` 组成。关系工作集按 correction、当前渠道未决 draft、最多 12 条当前渠道真实收发、最多 3 条背景排序，关系 JSON 目标不超过 3000 字符。旧记录默认不注入；按需搜索后结果以 tool 消息进入下一次请求。参考资料按 Skill 路由读取 1-3 份，而不是全量拼接。

### 功能需求

#### FR-1 schema v5

新增 `relationship_event_search_documents`：保存 event/person ID、原文副本与 SHA256、增强 JSON、扁平增强文本、增强来源/版本/状态。原文和增强文本均使用 MySQL `FULLTEXT ... WITH PARSER ngram`。

新增 `relationship_event_enrichment_jobs`：保存一个事件对应的 prompt 版本、`pending/running/done/failed`、attempts、无正文错误码/摘要和时间戳，支持断点续跑。

迁移先创建并填充新表，再删除旧 `relationship_event_index_jobs` 与 `relationship_search_indexes`。不触碰仓库外共享 Milvus 服务、collection 或卷。

#### FR-2 写入时增强

`relationship_commit_turn.events[*]` 新增可选 `search_enrichment`：

| 字段 | 上限 |
| --- | --- |
| `summary` | 必填非空，240 字符 |
| `concepts` | 最多 8 项，每项 40 字符 |
| `aliases` | 最多 8 项，每项 60 字符 |
| `entities` | 最多 8 项，每项 60 字符 |
| `time_hints` | 最多 6 项，每项 60 字符 |

每个非 draft 事件必须在同一事务 upsert 检索文档。增强缺失/非法时写 `raw_only` 并排队，不能阻断权威事件。重复提交只能补全缺失增强，空值或非法值不得覆盖已有增强；权威原文始终从 `relationship_events` 读取。

draft 不增强。correction 正常增强，但增强内容只能从该事件原文提取，不得补造人物、原因、态度或结论。

#### FR-3 MySQL 三分支检索

每个分支最多 40 个候选：

1. 原文精确/子串，权重 1.5。
2. 原文 ngram FULLTEXT，权重 1.0。
3. 增强文本 ngram FULLTEXT，权重 1.25。

以 RRF `k=60` 融合。所有 ID 必须按当前 binding、可选 channel 和 draft 合同回权威表 hydrate。命中旧事件后递归加载最多 8 层 correction closure，并把明确纠正在旧记录前。

返回字段仅包括权威事件 ID、正文、类型、角色、证据种类、渠道、时间、supersedes ID、命中来源、融合分数和截断状态。增强 JSON/文本不能返回。

#### FR-4 模式与保守口径

`retrieval.effective_mode` 只为：

- `mysql_enriched`：当前人物至少有增强文档。
- `mysql_raw`：尚无增强覆盖。

权威事件、检索文档或增强覆盖不一致时返回 `degraded=true`、`degradation_reason=incomplete_enrichment`。这不是数据库失败；原文分支仍可服务。零结果只能说“本次未检索到相关记录”，不得写成“从未发生”。真实数据库异常仍失败关闭。

#### FR-5 历史补强

回填覆盖活动和归档人物的 `received`、`sent`、`background`、`analysis`、`correction`，不包含 draft。operator 显式运行 queue/work/status，supervisor 不自动执行。

每批最多 8 条，序列化输入不超过 12000 字符；调用当前 Responses-compatible 远程主模型，使用严格结构化 function output。worker 不保存原始模型 response，不记录聊天正文，错误只存类型与有界摘要。source hash 防止在事件变化后写入陈旧输出。prompt 版本变化可重新排队已完成任务；不同版本的运行中批次不得混写。

#### FR-6 benchmark

保留 120 条、六类中文合成数据与固定 40/80 split。独立且为空的 benchmark 数据库填充到 10000 条，执行与线上相同的 ngram/RRF 和纠正闭包。数据库名必须以 `goutoujunshi_benchmark` 开头，避免写入权威库。报告分别给出复用连接的 SQL 核心延迟与按线上 repository 连接边界执行的数据库路径延迟，性能门槛以后者为准。

可选 `--answer-eval` 对 80 条 frozen 分别提供全量合成历史和 MySQL Top-8，要求模型结构化返回关键 event IDs 与 `advance/observe/stop/clarify/support`，据此计算事实覆盖和行动一致。

### 业务与隔离规则

- 同一人物默认跨渠道读取；显式 channel 时严格过滤。
- draft 必须显式 channel 且只走原文精确/子串。
- correction 不覆盖历史，但搜索排序必须让它优先。
- 搜索结果不会自动写回事件、快照或 owner 记忆。
- `raw_only` 不是失败，增强也不是事实。
- MySQL/binding 不明确时不搜索、不分析、不记录。
- 远程历史回填与当前主聊天处于同一信任边界，但实际批量外发仍必须再次授权。
