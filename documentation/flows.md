# 关键流程

本文先记录产品建议流程，再记录 Hermes 私有运行时的持久化与运维链路。前八节适用于 Codex Skill；后续章节只适用于已部署并正确配置的 Hermes 私有环境。

## 1. 男性找女友通用路径

**前置条件**：用户希望自然发展女朋友关系，可能没有具体对象
**成功结果**：用户知道当前阶段，并得到一个可持续的推进、观察或停止动作

1. 没有具体对象时，了解用户的真实生活、常见认识渠道、主要障碍与可接受的主动方式，不强制建立虚构对象档案。
2. 从朋友、学校、工作之外的兴趣活动或合适平台中，选择一个能长期参与且不依赖伪装的认识入口。
3. 出现具体对象后建立独立档案，从共同场景和真实细节开始互动。
4. 用持续主动、内容延展、时间投入、邀约回应和现实兑现判断互惠，不凭表情或一次热聊定性。
5. 互动稳定时提出一次具体、低压力、方便拒绝的邀约；线下重点观察双方相处体验和适配。
6. 双方持续投入并完成现实见面后，帮助用户具体表达喜欢和关系意愿。
7. 明确拒绝立即停止；一次软拒绝后先收住，只有新的自然契机且没有明确拒绝时再邀请一次；持续低互惠时退出并回到自己的生活和其他可能。

**节奏边界**：不设置脱单期限、周任务配额或成功保证；“顺其自然”是主动但不强求，不是被动等待。

## 2. 首次使用与建档

**参与者**：用户、Codex代理
**前置条件**：当前任务中不存在完整用户档案
**成功结果**：形成最小必要档案，并确定眼前问题和情绪强度

1. 用户显式调用 Skill 或提出符合描述的恋爱问题。
2. 代理先处理紧急情绪或必须马上回复的事项。
3. 没有具体对象时，代理只收集本人现状、主要优势和短板、常见认识渠道、目标与障碍。
4. 出现具体对象时，代理再收集本人MBTI和主观综合评分，并为一个或多个对象收集代号、MBTI、主观评分和关系阶段。
5. 代理了解关键事件、联系频率、双方投入、主要障碍、目标和情绪强度。
6. 代理复述档案，标记未知与矛盾，不填造缺失事实；每个对象保持独立。

**隐私边界**：只需使用代号；不需要真实姓名、地址、账号、身份证件或私密照片。

## 3. 常规关系分析

**前置条件**：拥有足够的用户叙述或档案
**成功结果**：用户获得可解释、可执行且保留选择权的建议

1. 用简短语言确认情绪与内在冲突。
2. 把叙述拆分为已知事实、合理推测和关键未知。
3. 根据场景读取必要参考文档。
4. 判断当前处于增加机会、建立互动、观察互惠、自然邀约、线下适配、确认关系、经营关系还是退出阶段。
5. 比较互惠、可靠、吸引、价值观、现实可行性、风险和机会成本。
6. 给出明确首选建议和关键理由。
7. 必要时提供稳健、策略或强势版本。
8. 收束为一件小事、观察窗口、停止条件和反馈信号。

**拒绝路径**：若用户要求实施违法、强迫、跟踪、诈骗或绕过同意的行为，代理拒绝该操作部分，解释风险并提供低风险替代。

## 4. 聊天材料分析与即时回复

1. 判断素材来自聊天截图、导出文本、复制对话、用户转述、通话、线下互动或混合来源。
2. 只把可确认的原文、发送者、顺序、间隔和行为写入事实；把含义解释放入推测。
3. 先处理用户当下情绪，再判断本轮主要目标是承接、调侃、推进、邀约、澄清还是收线。
4. 用户只要一句回复时，第一屏先给一条符合用户口吻、可直接发送的首选成品。
5. 按对方积极、含糊或拒绝反应给出后续分支；需要练习时每轮只模拟一条回复并等待用户接话。

## 5. 主动约会与第一次见面

1. 没有明确拒绝或不适时，给出至少一个主动联系、具体邀约或真实表达动作。
2. 第一次见面建议保持简洁，覆盖可交谈的地点、共同体验、具体欣赏和结束时的真实反馈。
3. 根据双方对恐怖、密闭、运动、噪音和人群的偏好选择活动，不把“吊桥效应”写成保证吸引的公式。
4. 肢体互动结合关系与现场适当创造自然、低强度、可退出的机会，并根据对方反应调整。
5. 一次含糊不等于永久退出；没有明确拒绝时可在合理间隔后换时间或场景再邀请一次。

## 6. 多目标对象比较

1. 为每个对象保留独立代号与事件记录。
2. 不用一个对象的MBTI、行为或话术填补另一个对象的信息。
3. 分别评估互惠、可靠、相处体验、现实可得性和长期风险。
4. 比较“高评分但不可得”和“评分较低但互惠稳定”的真实差异。
5. 保留“暂不选择任何人”作为合法选项。

## 7. 高情绪强度

1. 先缩小时间范围，避免连发、报复、突然删除或其他不可逆动作。
2. 建议暂存消息、离开刺激源或联系可信的人陪伴。
3. 在情绪下降后再进入事实分析和策略选择。
4. 若存在立即自伤或伤人危险，转入紧急支持，不继续只给恋爱话术。

## 8. 暴力、控制与危机

1. 识别暴力、性胁迫、跟踪、财务控制、隐私威胁或诈骗信号。
2. 读取法律安全与危机转介文档。
3. 优先人身安全、可信支持、证据保存和当地专业服务。
4. 不建议用户在不安全环境中单独摊牌或以伴侣咨询替代安全计划。
5. Skill只提供一般信息；现实紧急情况由当地紧急服务和合格专业人员处理。

## 9. 飞书消息接入与人物隔离

**触发**：飞书消息到达 Hermes Gateway
**成功结果**：只在 owner 与人物/群绑定明确时加载对应上下文；不满足条件时失败关闭

1. `pre_gateway_dispatch` 只接管 Feishu 平台事件，并优先处理 `/relation`、`/relationship` 与 `/me` 命令。
2. 普通消息必须来自 `GOUTOUJUNSHI_OWNER_ID`。插件为 owner 群设置 `auto_skill=goutoujunshi`。
3. 插件从 MySQL 解析当前 chat binding：
   - 未绑定普通群只加载 owner 本人记忆，可以回答一般问题。
   - 未绑定群若包含具体女生、聊天截图、怎么回复或关系判断，立即提示先绑定，本条不记录、不分析。
   - 已归档的 managed chat 不退回普通群；profile route 尚未切换到 `goutoujunshi` 时要求稍后重试。
4. 已绑定群只加载当前人物快照、当前渠道、当前草稿和有界事件工作集；旧事件通过 `relationship_search_events` 按需查询。
5. 插件向会话写入独立的 owner 与 relationship 签名令牌，再允许模型调用受限工具。
6. 数据层或 session store 异常时返回失败关闭结果，不让模型在无权威上下文下猜测。

## 10. 单轮关系提交与只读投影

**入口**：`relationship_commit_turn`
**成功结果**：本轮确认事实、建议草稿和必要快照以一次事务提交，并异步刷新投影

1. 工具校验 relationship token 与当前 session、chat、relationship binding 一致，并从服务端保存的 message source 取得去重依据。
2. 一轮最多写入 12 个事件，最多一个 `current_inbound`；保留显式确认兼容路径。普通 owner 消息到达时，hook 已先按同人物同渠道规则默认追加上一草稿的 `sent`；命令不触发，明确“没发/未发送/还没发/没采用/改了”则追加 correction。
3. 事务内依次写入事件、精确 `draft` 正文和快照变化。每个非 draft 事件同时生成 MySQL 检索文档；合法 `search_enrichment` 写为 `enriched`，缺失或非法时写为 `raw_only` 并排队，不阻断权威事件。无内容、未知事件类型、非法渠道或不安全确认会整体失败。
4. `dedupe_key` 和稳定的 external message id 使重复工具调用返回原事件而不重复追加。
5. 只有事务产生实际变化时才排入一个待处理 `export_jobs`。
6. exporter 从 MySQL 重新读取完整人物/事件数据，原子替换 `.local/relationships/<slug>.md` 并设置只读。
7. 投影失败会记录 `failed` 与错误，supervisor 后续重试；MySQL 提交仍是权威结果，投影不是回滚源。

## 11. 登录自启动与健康维护

**触发**：Windows 登录计划任务 `Hermes-Goutoujunshi`
**成功结果**：本机 MySQL、Gateway、Feishu route 和投影队列维持可服务状态

1. 计划任务运行 `scripts/Run-Goutoujunshi.ps1`，互斥锁防止重复 supervisor。
2. supervisor 导入受保护的 Hermes `.env`，保持 Ubuntu WSL 可用，并通过 WSL manager 启动 `mysql_container`。
3. `goutoujunshi_cli.py reconcile-config` 从 MySQL 活动绑定重建 profile routes，同时将免 `@` allowlist 规则镜像到 Feishu adapter 的 `extra.group_rules`。
4. supervisor 确保 Hermes Gateway 进程存在并检查 Feishu 连接状态。
5. 每轮重试关系投影、清理过期临时媒体；每天创建一次 MySQL dump 并清理超过 30 天的本地备份。
6. supervisor 不处理历史补强任务，避免日常启动隐式外发关系正文。单轮异常写入本地日志并等待下一轮，不代表服务已经恢复。
7. `Control-Goutoujunshi.ps1 -Action Stop` 停止计划任务，正常停止 Gateway 和 MySQL，再终止整个 Ubuntu WSL；其他在该发行版运行的程序也会停止。

本节只描述脚本定义。当前计划任务、容器、Gateway 和飞书连接是否健康，需要独立的运行态检查。

## 12. MySQL 增强检索与历史补强

1. `relationship_search_events` 先解析一个当前活动 binding。`channel` 省略表示该人物全部渠道；显式渠道才过滤。`include_drafts=true` 必须指定渠道，draft 只走原文精确/子串分支。
2. 搜索并行形成三支最多 40 条候选：原文精确/子串、原文 ngram FULLTEXT、增强文本 ngram FULLTEXT。固定 `RRF k=60`，权重依次为 `1.5 / 1.0 / 1.25`。
3. 融合 ID 必须按当前人物、可选渠道和 draft 合同回 `relationship_events` hydrate；补强文本仅参与排序，不作为事实返回。命中旧事件时递归加载 correction，并把 correction 放在旧记录前。
4. 默认返回 8 条，单条权威正文最多 1200 字符，总正文最多 6000 字符。`mysql_enriched` 表示至少有增强覆盖；覆盖不完整返回 `mysql_raw` 和 `incomplete_enrichment`。零结果不能写成从未发生。
5. schema v5 会为全部现有非 draft 事件创建 `raw_only` 文档和 pending 任务，并删除两个旧 MySQL 向量派生表。实际迁移必须单独授权。
6. 获准后，operator 显式运行 `enrichment-backfill` 统一 prompt 版本，再反复运行 `enrichment-work --limit 8`，最后用 `enrichment-status` 核对；达到 5 次上限的失败项需显式 `enrichment-retry-failed`。每批输入不超过 12000 字符，当前远程主模型只返回结构化增强，不保存原始响应/正文日志。
7. 新 prompt 版本可把已完成事件重新排队；失败或中断通过 attempts/status/started_at 续跑。回填覆盖活动和归档人物的 `received/sent/background/analysis/correction`，不包含 draft。
